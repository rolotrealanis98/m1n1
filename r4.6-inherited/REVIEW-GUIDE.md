# r4.6 review guide

**Stage-3 release acceptance is blocked by retained test failures. Firmware binaries: not built. Hardware/Windows execution: unverified.** The code fixes and host evidence are supplied for coordinator review; this package does not claim that stage 3 may now be run on hardware.

**Intentional READ policy change:** `source/src/hv/win/s1/hv_nvme_queue.c:691` refuses guest past-end/overflowing READs with `VNVME_SC_INVALID_FIELD`, increments a counter, and does not abort the disk. Even a past-end READ exceeding MDTS takes this normal-error path. `source/src/hv/win/hv_win_storage.c:172` exposes the counter as `storage_stat(12)`. A following valid READ/WRITE succeeds. An out-of-range WRITE (`hv_nvme_queue.c:636`), invalid absolute driver range, or direct backend confinement violation still freezes. The lower `native_window.c:236` READ guard remains terminal; it must never receive a guest past-end probe.

All short filenames in the tables refer to `source/src/hv/win/s1/` unless otherwise stated.

## Verification interpretation

The r4.5-with-overlay baseline was actually rerun: stages 0/1/2/3 pass 48/54/54/196 scenarios; stage 3 catches 86/86 native mutants. r4.6's unchanged-policy expectations retain failures: 47/48, 51/54, 51/54 and 186/196. Added r4.6 scenarios and targeted mutants are separate evidence, not a substitute for declaring those failures.

The retained failures are:

- stage 0: `r45_stage` sends a WRITE to the read-only namespace before expecting successful later FLUSHes; new C9 freezes immediately.
- stages 1/2: `r45_stage` and `r45_stage_corrupt` similarly send a guest RO WRITE before CANARY. `r45_link` expects CANARY allowed after its loop has already exercised HV_START; the new guard refuses it.
- stage 3: `e2e_reads` expects clean shutdown after an above-cap READ; `allowlist`/`rw_requires_flag` expect the old nonterminal `-1`; `rw_basic` and `secA_rw_write_0..5` expect four physical WRITEs, while two 256-block requests now split into sixteen plus two one-block writes (18).

No assertions for these cases were changed. Only the three READ-refusal expectation edits listed in NOTES.md were made. The original `stage_inspection.py` fails at its old function-location assertion; the additional r46 inspection checks the same properties at `xfer_owned`, including rejecting three invalid stage builds. `review-tests-r4/run.py` has a pre-existing missing-header build failure on both baseline and r4.6.

`TEST-RESULTS.json` contains final receipts, exact counts, failures, mutant outcomes and source manifest hash. Native mutants with stale source anchors are invalid, not killed; follow-up cases distinguish real regression detection from an already-failing baseline. Existing 3 gap-mutant survivors remain explicitly reported.

The falsifiable offline twin runs without firmware against this source, accepts malicious out-of-window writes in its fake, and independently checks the image, command log and counter. Baselines at caps 1/256 must pass; M1–M4 must fail. Stage twins also test restoration and four loosened stage edges. These synthetic-image results do not establish real disk persistence, physical DMA coherence, firmware completion ordering, Windows operation, capsules/launcher readiness or safe hardware recovery; all remain **unverified**.

Final count summary: 140/140 added scenarios (28/31/31/50 across stages), 23/23 new mutants, 84/86 inherited native mutants (two invalid anchors named in NOTES.md), 44/44 r4.5 additional mutants with passing added cases, 7/7 overlay mutants. Both final twin receipts and the broad host suite pass. The unchanged incompatible native assertions still prevent release acceptance. Source patch application was independently checked against a fresh r4.5 source copy.
